# GD with GD Demoland

An in-browser HTML/CSS editor and demo gallery for teaching. Each demo is a live,
editable page: students edit code on the left and see the result update on the right,
with optional hints pinned to specific lines. A small static-site generator turns a
folder of `.demo` files into a deployable, SEO-friendly site organized as
**books → chapters → demos**.

No framework and no runtime CDN. CodeMirror 6 and its helpers (acorn, js-beautify, the
language modes) are **pre-bundled once** into a single self-hosted file, `lib/codemirror.js`,
so pages load nothing from a third party. The build script (`build.mjs`) uses Node built-ins
only; see `lib/README.md` to regenerate the bundle.

Demos can be **multiple files** (HTML/CSS/JS + media), navigate between pages, show media
previews, and expose per-demo config for panels, settings, and locking ~ all still authored
in a single `.demo` file. See the sections below.

---

## Quick start

```bash
node build.mjs          # regenerate the whole site into the project root
```

Then serve the folder with any static server (Live Server, `npx serve .`, etc.) and
open `index.html`. There is no dev server and no watch mode ~ re-run `node build.mjs`
after editing a `.demo`, `collection.json`, or any source file, and refresh.

To deploy: push the generated files to GitHub Pages (or any static host). The build
writes straight into the project root, so the repo root is the deploy root.

## Project structure

```
collection.json          # the site outline: books → chapters → demos (you edit this)
demos/*.demo             # one file per demo: lesson, hints, config, and file(s)
editor.template.html     # the shell every demo page is built from
style.css                # all styles, hand-maintained (build minifies -> style.min.css)
editor.js                # the editor app (CodeMirror, tabs, panels, console, nav, embeds)
chrome.js                # shared page chrome: topbar nav popup, tooltips, footer (all pages)
landing.js               # landing-page interactions
lib/codemirror.js        # pre-bundled CodeMirror 6 + acorn + js-beautify (self-hosted)
build.mjs                # the static-site generator

# generated by build.mjs (don't hand-edit ~ they're overwritten):
index.html                       # homepage (lists books)
<book>/index.html                # book page (lists chapters + demos)
<book>/<chapter>/index.html      # chapter intro page (lists that chapter's demos)
<book>/<chapter>/<demo>.html     # the demo editor page
style.min.css                    # minified stylesheet
sitemap.xml, robots.txt          # only when siteUrl is set
```

The build only removes and regenerates the book folders and the top-level
`index.html` / `sitemap.xml` / `robots.txt`. It never wipes the whole directory, so your
source files are safe.

## Adding or editing content

### 1. `collection.json`

This is the table of contents. Top level:

```json
{
	"title": "GD with GD Demoland",
	"siteUrl": "https://demoland.gdwithgd.com/",
	"books": [ … ]
}
```

- **`title`** ~ used in page `<title>`s and shown in the topbar.
- **`siteUrl`** ~ your canonical origin. Required for correct canonical tags and the
  sitemap; leave it empty during local work if you like (those are then skipped).

Each **book** has an `id` (used in the URL), `title`, optional `description`, and a list
of **chapters**. Each chapter has an `id`, `title`, optional `description`, and a list of
**demos**. Each demo points at a `.demo` file:

```json
{ "id": "flexbox", "title": "Layout with Flexbox", "file": "demos/flexbox.demo" }
```

The `id`s become the URL path (`/<book>/<chapter>/<demo>.html`), so keep them short,
lowercase, and hyphenated.

**Delisting (hiding from the menus).** Add `"hidden": true` to any book, chapter, or demo
to drop it from every menu ~ the homepage, book/chapter pages, the nav popup, the prev/next
arrows, and the sitemap. Its page is **still built**, so a direct link keeps working; it's
just unlinked. Remove the flag to list it again. Example: `{ "id": "draft", "title": "Work
in progress", "file": "demos/draft.demo", "hidden": true }`.

### 2. `.demo` files

A demo is a plain-text file split into labelled sections. Headers look like
`=== KEYWORD ===` (or `=== FILE name.ext ===` / `=== MEDIA name.ext ===`), each on its own
line. A minimal single-file demo:

```
=== TITLE ===
Layout with Flexbox

=== INFO ===
Markdown for the info panel. Supports headings, **bold**, `code`,
lists, > blockquotes, and file trees (see below).

=== NOTES ===
[
  { "line": 8, "text": "Explanation…", "open": true },
  { "line": 11, "text": "Explanation…", "file": "index.html" }
]

=== HTML ===
<!DOCTYPE html>
<html> …starter code the student edits… </html>
```

**Sections:**

- **`TITLE`** ~ falls back to `collection.json`'s title if omitted. The info panel's H1 and
  the "Demo #.#" bubble are generated from the title automatically; a leading `# Heading` in
  `INFO` is dropped so it isn't duplicated.
- **`INFO`** ~ Markdown for the info panel. Optional. Supports headings, bold, `code`, lists,
  blockquotes, **file trees**, **buttons**, and **FAQ accordions** (see the subsections below).
- **`CONFIG`** ~ optional JSON of per-demo options (see *Config* below).
- **`NOTES`** ~ a JSON array of line hints. Each has `line` (1-based, relative to the
  **whole `.demo` file** ~ the build converts it to be per-file), `text`, optional
  `open` (open by default), and optional `file` (which file the hint pins to; defaults to the
  entry). Omit or use `[]` for none.
- **`HTML`** ~ legacy shorthand for a single `index.html` file (kept for backward compat).
- **`FILE name.ext`** ~ a named file (see *Multi-file demos*). Use one per file instead of
  `HTML` when a demo has more than one file.
- **`MEDIA name.ext`** ~ a media file referenced by its real location (see *Media*).

Trailing commas in `CONFIG`/`NOTES` JSON are tolerated. After editing, run
`node build.mjs` and refresh.

### Multi-file demos

Give a demo several files with `=== FILE name.ext ===` sections instead of a single `HTML`
section. Each file becomes a tab in the code panel (HTML/CSS/JS get language modes; JSON/text
too). File names may include folders (`pages/about.html`, `css/style.css`).

```
=== CONFIG ===
{ "allowAdd": true }

=== FILE index.html ===
<!doctype html>
<link rel="stylesheet" href="css/style.css">
<h1>Hi</h1>
<a href="pages/about.html">About</a>
<script src="app.js"></script>

=== FILE css/style.css ===
h1 { color: rebeccapurple }

=== FILE app.js ===
console.log("hello")

=== FILE pages/about.html ===
<!doctype html><h1>About</h1><a href="../">Home</a>
```

- **Entry** ~ the preview always starts on `index.html` (the un-renameable main tab). If a demo
  somehow has no `index.html`, the first HTML file is used.
- **Local references are resolved and inlined** for the preview: `<link>`/`<script src>` to
  local files are inlined, media is swapped for its real URL, and relative paths (`./`, `../`,
  root-relative, folder → `index.html`) all resolve. External `http(s)` URLs are left alone.
- **Multi-page navigation** ~ clicking a link to another local HTML file switches the preview
  to that page; a dot in the tabs marks the previewed page, and a "Currently previewing: …"
  bar appears above the preview.
- **Editing** an HTML file previews it; the info panel auto-lists the files as a tree.
- `allowAdd: true` lets learners add / rename / delete / reorder / upload files (and drag files
  or a folder onto the editor). Downloads come out as a `.zip` for multi-file demos.

### Media

Reference images, fonts, audio, or video that already live somewhere on the site ~ nothing is
inlined into the `.demo`. The section header is the file's **path inside the demo project**;
the body is **where the file actually lives on the site** (root-relative, or an absolute URL):

```
=== MEDIA assets/logo.png ===
media/brand/logo.png
```

Wherever the code references `assets/logo.png` (in `<img src>`, CSS `url()`, etc.) the preview
rewrites it to the real location. In the editor a media file's tab shows a **preview** (image,
audio/video player, or font specimen) with its type, size, and dimensions/duration ~ not code.
Uploaded media (via drag-drop) is stored inline as a data URL.

### Config

The optional `=== CONFIG ===` section is JSON:

```json
{
  "allowAdd": true,
  "notesExpanded": true,
  "panels": { "info": true, "code": true, "preview": true, "console": true },
  "settings": { "wrap": true, "syntax": true, "autoclose": true,
                "autocomplete": false, "warnings": true, "zoom": true },
  "lock": ["warnings", "wrap", "prettify"]
}
```

- **`allowAdd`** ~ allow learners to create/rename/delete/reorder/upload files.
- **`notesExpanded`** ~ `true` opens every note by default when the demo loads (instead of the
  per-note `open` flag).
- **`panels`** ~ show/hide each panel. `info`/`code`/`preview` are booleans (if all three are
  off, all show). `console` (inside the preview panel) is `true` (show) or `false` (hide it).
  Setting `preview: false` **and** `console: true` gives a **console-only** panel: the preview
  iframe is hidden behind a "preview disabled" overlay and the console fills the panel on its
  own. Resizers appear only between two visible panels.
- **`settings`** ~ starting on/off for `wrap`, `syntax`, `autoclose`, `autocomplete`,
  `warnings`, `zoom`. Learners can still toggle these unless locked.
- **`lock`** ~ an array of setting keys to lock; a locked toggle shows disabled with a
  "Setting locked for the current demo" tooltip. Lockable keys: `wrap`, `syntax`, `autoclose`,
  `autocomplete`, `warnings`, `zoom`, and `prettify` (the reformat button).

### File trees

Inside `INFO` (or anywhere Markdown is rendered), a fenced block tagged `tree` renders a
styled file tree. Indentation (2 spaces or a tab per level) sets nesting; a trailing `/` marks
a folder:

````
```tree
src/
  index.html
  css/
    style.css
  app.js
```
````

Multi-file demos also get an auto "**Files in this demo**" tree in the info panel, in the order
the files appear in the `.demo`.

### Buttons (call-to-action links)

Put `[[Label]](url)` on its own line to render a big button. External URLs (`http(s):`,
`mailto:`, `//`) open in a new tab and get a ↗ arrow; internal paths (e.g. a link to another
demo) open in the same tab. Consecutive button lines flow together in one row.

```
[[Read the guide]](https://example.com/guide)
[[Next demo]](../flexbox/wrapping.html)
```

### FAQ accordions

A fenced block tagged `faq` renders a click-to-expand accordion. Each question is a line that
starts with `Q:`; everything up to the next `Q:` is that answer, rendered as Markdown:

````
```faq
Q: What is a demo?
A demo is a single editable example with a live preview.

Q: Can I add my own files?
Only when the demo enables `allowAdd`.
```
````

## How colors work

Books cycle through a fixed palette by their order (book 0 = pink, book 1 = green, …).
Demos cycle by their position **within their book**. The book/chapter landing pages use a
neutral accent; the demo pages and the colored accents in the nav popup come from these
rules. The palette lives in two places that must stay in sync: `build.mjs` and `editor.js`
(and `nav.js` mirrors it for the landing-page popup).

## Blank editor

The build also emits a standalone editor at **`/editor/`** that isn't part of any book —
the same editor chrome wrapped around a three-file starter: `index.html`, `style.css`, and
`script.js`, with the HTML already linked to the other two. It has the info tab (basic
instructions you can edit), no hints, a random accent colour each time it loads, and instead
of prev/next arrows it shows an **Upload** button (pick multiple files or a whole folder);
users can also **drag files or a folder anywhere onto the page** to add them, with a
confirmation dialog (add to project vs. replace all, and a file-path field). Upload/drag-drop
works on any demo with `allowAdd`, not just the blank editor. The three starter files and the
instruction text live in `build.mjs` as `STANDALONE_STARTER` / `STANDALONE_STYLE` /
`STANDALONE_SCRIPT` and `STANDALONE_INFO`. (Because it lives at `/editor/`, don't give a book
the id `editor`.)

## Embeds

Any demo can be embedded as a slim widget via `…/<demo>.html?embed=<token>`. The token
encodes which panels to show, notes, read-only, and dimensions. Generate the snippet with the
**Embed** button in a demo's controls, or **"Embed this demo"** in the footer. In the dialog,
**Preview** and **Console** are separate checkboxes under *Panels* ~ check both for
preview+console, just one for preview-only or console-only. The dialog respects the demo's
config: panels it hides can't be embedded, and a console-only demo only offers Console.

## Notes for maintainers

- **Syntax warnings:** as the student types, each demo's code is statically checked
  (no execution) and problems show as a chip at the bottom-left of the editor with line
  numbers ~ click the chip to jump to the first, or the issue count to open the full list;
  each flagged line is also tinted. Each issue shows the language and line on top and a
  plain-language explanation below. Students can turn the whole thing off via the
  **warnings** toggle in the editor's view settings (on by default, remembered per browser).
  The checks target common beginner mistakes:
  - **HTML** ~ mismatched tags (`<div>…</span>`), unclosed tags, stray closing tags,
    unterminated `<!-- -->`, and attribute problems: a duplicate attribute, a missing `=`,
    an `=` with no value, an unclosed/mismatched quote, and a value with no attribute name.
  - **CSS** ~ missing colon (`color red;`), empty property or value, a likely missing
    semicolon (two declarations run together), unbalanced braces, unterminated
    comments/strings, and **unknown properties** (`colr`, `dispay`) ~ these are checked
    against the browser itself via `CSS.supports`, with a "did you mean …?" suggestion for
    likely typos. It ignores colons/semicolons inside `url(...)`, strings, selectors, media
    queries, and keyframes, skips custom properties (`--x`) and vendor prefixes (`-webkit-…`),
    and doesn't flag `@font-face`/`@page` descriptors, so valid code isn't flagged.
  - **JS** ~ each inline `<script>` is parsed with
    [acorn](https://github.com/acornjs/acorn) (loaded from esm.sh via the import map),
    which reports syntax errors at an exact position. A light scope analysis on top of the
    parse also flags **undefined names** (a function or variable that was never declared and
    isn't a browser global ~ catches typos like `gret()` or `consle.log`), **reassigning a
    `const`**, and **redeclaring** a name. Names are gathered across all of a demo's inline
    scripts, and browser globals are recognised via the runtime itself, so valid code stays
    quiet. The undefined-name check stands down automatically when the page loads any
    external `<script src>` (since that script may define globals it can't see).

  It only flags real syntax breakage and clear scope mistakes ~ property typos that browsers
  silently ignore (`colr: red` is caught, but a wrong *value* isn't) and dynamic patterns
  aren't second-guessed. Warnings are **off inside embeds**. The tag matcher tolerates
  HTML's optional-closing elements (`<li>`, `<p>`, `<td>`, …).
- **Cache-busting:** the build appends a content hash (`?v=…`) to `style.min.css`,
  `editor.js`, and `chrome.js` references, so redeploys don't serve stale assets.
- **The nav popup markup is baked** into every page by `build.mjs`; `chrome.js` only
  opens/closes it (shared across demo and landing pages). Anything with `data-nav-open`
  opens the menu (e.g. the info panel's demo header).
- **`style.css` is hand-maintained** and shared by every page type (editor, landing
  pages, homepage); the build minifies it to `style.min.css`. Validate brace balance after
  edits.
- **Demo numbers** show as `chapter.demo` (e.g. `2.1`) in the nav, landing pages, and info
  bubble; the topbar shows "Demo N of M" on desktop and `#.#` on mobile.
- **The CodeMirror bundle** (`lib/codemirror.js`) is pre-built; regenerate it per
  `lib/README.md` if you change editor dependencies.
- The fonts are referenced at the absolute path `/assets/fonts/…`, so the site expects to
  be served from the domain root (which the GitHub Pages + custom-domain setup provides).
